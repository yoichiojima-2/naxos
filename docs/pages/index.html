naxos · technical documentation

A managed-agent platform that runs entirely inside your own GCP boundary

naxos is a Google Cloud implementation of the Claude Managed Agents (CMA) object model — Agent → Environment → Session → Events — in roughly 10,700 lines of Python, TypeScript, and Terraform, all inside a single GCP project. Always available rather than always running: everything except Postgres scales to zero.

Why

The only reasons this platform exists

Hosted CMA runs the agent loop and the sandbox on Anthropic's cloud. naxos exists for the cases that structurally cannot leave the organization: the data boundary (model access via Vertex AI only), internal-system integration inside that boundary (self-hosted MCP to closed-network systems), and execution-level governance (human approval gates, an instant kill switch, per-tenant IAM, and a per-tool-call execution record you can hand to an auditor). A task that fits none of these axes belongs in the Claude app or hosted CMA — this platform deliberately does not compete on UX or feature velocity.

naxos-sbx-{env}

All control-plane state, including the tool_calls execution record. 19 tables, in-process migrations. The only always-on cost.

GCS · per-environment buckets

Session workspaces, SDK transcripts, published artifacts. Restored on wake, written back at checkpoint.

BigQuery · naxos_audit

runs + tool_calls, an append-only export written only by the control plane. Read access to other datasets is a per-environment opt-in; the audit dataset is never grantable.

Object model

Agent → Environment → Session → Events

An Agent is a versioned DB row (agent_versions, PK (agent_id, version)): instructions, model, tools, permission policy, vault / memory / skill references. Updates append immutable versions; each session pins one. An Environment is the tenant/isolation boundary — a per-environment service account, sandbox Job, and GCS bucket, fanned out by Terraform from terraform/environments.json. The API only registers rows; adding a tenant is one JSON entry plus terraform apply, never a new app.

A Session is durable state, not a process: metadata and an append-only event log (per-session seq) in Postgres; workspace and transcript in GCS. A container exists only while the session is actively processing. Events use the CMA vocabulary — 15 types, of which clients may send only user.message, user.interrupt, user.tool_confirmation, and user.custom_tool_result. GET /v1/sessions/{id}/events?stream=sse streams them with Last-Event-ID replay.

Memory stores are Postgres-backed, mounted as ws/memory/{store}/… on wake and written back at checkpoint. Stores can be renamed (PATCH) and deleted (DELETE refuses with 409 while attached to an agent's latest version or referenced by a non-terminated session, protecting sandbox writeback); listings report file counts and which agents use each store.

Governance

Built into the platform, not retrofitted

An execution record, not a chat log — every tool call an agent attempted is recorded by the control plane at the permission gate, the one point every call must pass. The row is committed before the tool runs, so a sandbox that dies mid-call still leaves evidence, and the decision is the gate's own rather than something the sandbox reported. One row per call: who asked, who approved it, the exact arguments its call_hash covers, the decision (auto_allowed | user_allowed | user_denied | not_allowed | killed | awaiting_confirmation) and what came back. It has no foreign key to the session, so deleting the conversation cannot erase what was done. Query it over /v1/tool_calls, export it as NDJSON, and read the archive in audit.tool_calls; every wake-to-idle burst lands in audit.runs with principal, tokens and cost.

Approval gate — the always_ask policy is enforced by a PreToolUse hook (not can_use_tool, which is shadowed by allowed_tools entries and the CLI's read-only auto-approval). Confirmations are keyed on sha256(tool_name + canonical input) because tool_use_id changes across resume. While a confirmation is pending the session idles with requires_action and the container is released — a blocked agent costs nothing, no matter how long the human takes.

Kill switch — agents.disabled is checked at session creation, event accept, wake, permission resolution, heartbeat, queue long-poll, and deployment fire. Budget — a per-session hard cap; on breach the session idles with budget_reached, and raising the budget is itself the resume signal.

Sandbox subsystems

Artifacts, schedules, skills

Three subsystems ride on the core objects as built-in MCP servers inside the sandbox — ordinary tool calls, so the permission gate, kill switch, and audit apply unchanged.

Artifacts (artifact_create/list/delete/share/unshare) are files an agent deliberately publishes: content goes straight to the environment's session bucket (10 MB cap), metadata is versioned through naxos-internal, and sharing mints a stable token URL that stays behind IAP — nothing ever becomes public. Schedules (schedule_create/list/delete) let an agent create durable Cloud Scheduler deployments for itself (created_by = agent:{session}, capped per agent) — the CLI's session-local cron tools are disallowed because in-container timers die at the next idle checkpoint. Skills are org-shared Agent Skills folders stored in Postgres, rebuilt into a read-only local plugin on every wake, with no writeback path — a prompt-injected agent cannot poison skills shared by every other agent. The control-plane image bundles sample skills plus Anthropic's official skills (docx, pptx, xlsx, pdf, mcp-builder, …) and seeds them create-once at startup.

BigQuery analysis is a declarative per-environment opt-in: a bigquery_datasets list in environments.json grants that environment's SA bigquery.jobUser plus dataViewer on exactly the listed datasets. A Terraform precondition makes the audit dataset permanently ungrantable.

Egress

Secrets the sandbox never sees

Vault credentials are stored as Secret Manager references. When a session's agent uses an MCP server with a matching credential, the control plane mints an opaque route token and rewrites the server URL handed to the sandbox to {egress}/r/{token}. The 99-line proxy verifies the caller's OIDC identity (its SA must equal the session's environment SA), resolves the token through naxos-internal, reads the secret (only sa-egress can), strips the incoming Authorization header and injects the real one, then forwards. A fully compromised agent can use a credential but can never read or exfiltrate it.

Hard constraints: Vertex AI is the only model exit (a Secret-Manager-held Anthropic API key remains a documented temporary exception until Vertex quota lands — open issue R2); governance lives in the control plane and harness where agent config cannot bypass it; the control plane never holds IAM-admin; everything scales to zero.
